# 报告模板骨架（report_template）

> 用途：组会汇报、成果汇报、项目进展、技术文档、调研报告。
> 调用方：research / dev。
> 原则：结论先行、证据可核、局限不藏、问题留白。

## 模板 A：科研组会周报（一页式）

```text
# 【标题：本周主题】

## 一句话结论
【给不看细节的人：本周主要做了什么、关键结果如何、下一步是什么。】

## 1. 背景与目标
- 为什么做：【课题背景】
- 本周目标：【可检查的目标】

## 2. 本周进展
- 【动作 1：读了/实现了/跑了什么】
- 【动作 2：...】

## 3. 关键结果
- 【指标/现象：数字或事实】
- 【表格/图占位：[待补]】
- 【与基线对比：...】

## 4. 问题与局限
- 【困难/失败/不确定性】
- 【风险：什么条件下会翻车】

## 5. 下一步
- 【行动】 → 【验收标准】
- 【行动】 → 【验收标准】

## 6. 讨论问题（留 2–3 个）
1. 【评审/导师可能会问的问题】
2. 【需要组会裁决的分歧点】
3. 【自己拿不准的地方】
```

## 模板 B：成果汇报（结题/里程碑）

```text
# 【成果名称】

## 一句话成果
【做了什么，解决了什么问题，用可观测结果说明。】

## 交付物
- 【模块/文档/代码/数据】
- 【使用入口/链接】

## 可观测结果
- 【指标对比：基线 → 当前】
- 【证据位置：[报告/数据/日志/截图]】

## 取舍与代价
- 【为了得到 A，牺牲了什么】
- 【仍然存在的问题】

## 后续
- 【继续做 / 不做的理由】
```

## 模板 C：技术文档（dev 场景）

````text
# 【组件/功能名】

## 是什么
【一句话：给谁用、解决什么问题。】

## 快速上手
```bash
# 安装/初始化/运行
```

## 接口
| 输入 | 类型 | 说明 | 必填 |
|---|---|---|---|
| `topic` | string | 【含义】 | 是 |
| `domain` | string | 【含义】 | 否 |

## 实现与边界
- 【关键机制】
- 【不做什么 / 已知限制】

## 错误处理
- 【常见错误与提示】

## 示例
【可运行示例】
````

## 使用说明

- 所有 `【】` 都要由调用方补全；事实/数字/引用必须可核验，写 `[待补]` 优于编造。
- 报告必须包含“问题/局限”和“下一步”，不能只报喜。
- 如果是科研场景，保留专家/导师的分歧与结论归属；模板只是表达容器。
