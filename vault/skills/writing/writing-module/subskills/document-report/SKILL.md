# 文档 / 报告写作（document-report）

> 属于 `writing-module` 子技能。
> 负责表达：把零散素材组织成结构清楚、读者可核对、可汇报的文档/报告。
> 不负责：核实论文/实验数据、判断研究价值、生成未经确认的结论。

## 触发条件

- research 模块需要组会汇报稿、成果报告、论文章节初稿、模拟问答稿时。
- dev 模块需要技术文档、架构说明、接口文档、复盘报告时。
- 用户要把一页笔记/会议记录整理成正式报告。
- 需要把多专家讨论/研究结论沉淀为可提交的书面材料。

## 动作

1. **解析输入**：确认 `topic/domain/audience/type/purpose/length/references`；报告类必须先确认“读者是谁、要在什么场合用”。
2. **搭骨架**：按场景选择结构：
   - 组会汇报：背景 → 问题 → 本周进展 → 方法/实验 → 结果/数据 → 局限 → 下一步 → 讨论问题。
   - 成果汇报：一句话结论 → 做了什么 → 可观测结果（数字/证据）→ 对比基线 → 不足与下一步。
   - 技术文档：用途 → 安装/上手 → 接口/配置 → 实现要点 → 错误与边界 → 示例。
3. **填充与标注**：只写调用方提供的素材；缺失的事实/数字/引用用 `[待补]`，不得臆测。
4. **写结论先行**：每节第一句先给结论，再给支撑；听众/读者 30 秒内能抓到重点。
5. **准备问答**：科研汇报额外生成 2–3 个“评审/导师最可能问”的模拟问答，标注问题来源。
6. **输出**：`text`（可提交的草稿）+ `placeholders` + `questions` + `notes`（指出哪些地方需要核验）。

## 报告骨架约定

```text
标题：
0. 一句话结论（给不看细节的人）
1. 背景与目标（为什么做，目标是什么）
2. 做了什么（按时间/模块，动作明确）
3. 关键结果（数字、图表、证据，必须带 [来源]）
4. 对比与取舍（与基线/替代方案比，说明代价）
5. 局限与风险（别只报喜）
6. 下一步（谁、什么时候、做什么、验收标准）
7. 讨论问题（给组会/评审留的 2–3 个问题）
```

## 边界

- 不代替论文/数据：公式、数字、图表引用必须回到原文或原始数据，写 `[待核对]` 也可以。
- 不美化结果：报告不是宣传稿；坏结果、失败分支、风险要如实呈现。
- 不虚构研究价值：不写“填补空白”“开创先河”等无依据评价。
- 不覆盖专家判断：科研模块/导师给的结论与分歧必须保留，不能并入单一叙事。

## 示例占位（可替换为真实场景）

```text
场景：科研组会周报
【对象】课题组；【类型】report；【长度】一页
【素材】读了 2 篇论文、跑了一组消融、发现 baseline 强、下步试新损失
【骨架】一句话结论“本周确认当前 baseline 仍强，新损失暂未带来增益”→ 进展 → 数据[待补] → 局限 → 下一步 A/B。
```

## 反例

| 不要 | 改为 |
|---|---|
| “经过深入研究，效果显著提升” | “相比 baseline，指标从 X 提升到 Y；数据见 [图/表待补]。” |
| “本工作具有重大创新意义” | “这项工作与已有方案的不同点在于：……；是否成立仍待实验验证。” |
| “结果如下：”无数据 | “结果如下，数字待核对：[表格占位]。” |

## 2026 深度补强（Round 34）

> 新增 8 条可执行规则，覆盖：受众分层、结论先行、数据表格、版本与评审流程。来源编号对应 `SOURCES.md` 的 Round 34 表；每条尽量给出可复制的反例/示例。

### 1. 受众分层：先切“任务/决策”，再切“专业层级”

- **规则**：动笔前写出 2–3 个读者画像（决策者 / 执行者 / 复现者），并明确每个画像“今天要做什么决定、必须读哪几节”。不同受众的素材放进不同正文/附录，不要混排。
- **示例**：组会报告：正文给导师/评审（结论 + 证据 + 风险），实验配置、参数表、原始命令放附录给复现者。
- **反例**：把“实验细节”嵌在“关键结果”段中间，导致决策者跳读、复现者还要回原文找。

### 2. 标题也是结论/问题界面

- **规则**：章节标题优先用“结论句”或“用户会问的问题”，少用“概述/讨论/背景/补充”等主题词；标题本身应帮助读者 30 秒勾勒路线图。
- **示例**：把 `结果` 改为 `基线仍强，新损失暂未带来增益`；把 `方法` 改为 `我们如何排除数据泄漏`。
- **反例**：`一般说明`、`Scope`、`Application`、`补充材料` 这类靠上下文才能理解的标题。
- **来源**：R34-4、R34-3。

### 3. 主句先行，例外后置；短例外可前置

- **规则**：每段先给主结论/主规则，再给例外与条件；若例外仅几个词且前置可避免误导，就前置；若条件有多个，用编号/项目列表展开，不要塞进一句长句。
- **示例**：改前 `除非已提交最近简历，否则必须提交包含……的简历`；改后 `除非已提交最近简历，否则必须提交包含以下信息的简历：1) …；2) …。`
- **反例**：把“例外 + 主规则”全部压在一个长句里，读者要先读例外才知道规则。
- **来源**：R34-3。

### 4. 表格准入：先问“两句话能否说清”

- **规则**：能用一两句话说清就不用表；表只用于矩阵/多维对比/需要横向扫描的数据。表格必须带：编号 + 标题、列头含单位、有逻辑的行列次序、来源/footnote；不能留空单元格，空值写 `None` 或 `不适用`；`Description` 列放最右；单元格内不放长句。
- **示例**：特性对照矩阵（列=方案，行=能力，值=`有/无/受限`）适合用表；单条结论的“方法/结果/局限”适合用列表或小节。
- **反例**：8 列表格中 5 列几乎全为空、单元格塞 40 字散文——这种“表”不如换成列表 + 子标题。
- **来源**：R34-5、R34-6、R34-7。

### 5. 数字可追溯：一个数字对应一行证据

- **规则**：每个关键数字必须能在表格或原始数据中定位到一行；列头注明时间范围、基线、样本量/单位；缺数据写 `[待补]` 并给出缺失原因，不写“暂无数据”。把“效果显著”换成“A→B 提升 X（±Y，n=Z）”。
- **示例**：表格第 4 行 `消融实验 | 新损失 | 0.92 | 基线 0.89 | n=128 | [来源：exp.log 第 41 行]`。
- **反例**：正文写“多个实验均显著优于基线”，但表格没有行号、单位或样本量。
- **来源**：R34-5、R34-6、R34-7。

### 6. 版本元数据：报告头部固定 Version/Status/Date/Owner/Reviewer

- **规则**：每次交付在文件头写版本号、状态（草稿 / 评审中 / 已发布 / 已过期）、ISO 8601 日期、作者/维护者、评审人；版本号变化必须对应 changelog 条目（Added/Changed/Fixed/Removed），并用 `Unreleased` 收集在途变更，发布时并入正式版本。
- **示例**：`Version: 0.4 · Status: 评审中 · Date: 2026-03-08 · Owner: 张三 · Reviewer: 李四`，下方 changelog 先记 `Unreleased`。
- **反例**：`报告v2最终版_final2.docx`——没有状态、日期、评审人，也不可追溯“v2 改了什么”。
- **来源**：R34-10、R34-12。

### 7. 评审流程：Better/Best，别用代码评审标准卡文档

- **规则**：文档评审目标是“更好而不是最好”；评审者优先给替代建议而非模糊意见，避免“你应该顺便……”；只在文档确实变差时才拦下；作者不为琐碎争论消耗周期。文档变更应与代码/决策同批提交，并可把“缺文档”作为功能合并门禁。
- **示例**：评审意见写“建议改成：先给结论再给依据”，而不是“这段读起来不舒服”；作者可依据 Better/Best 先合入改进，再开 follow-up CL/修订。
- **反例**：把文档评审当代码 LGTM 卡得很死，导致小改进也迟迟不落；或只写“请优化”不给替代方案。
- **来源**：R34-10、R34-11。

### 8. 文档健康度：像 bonsai 一样常修剪

- **规则**：保持“小而新鲜”的文档集，不要堆大量半死文档；文档随代码/决策一起更新；对常见知识链接到权威源而非重复撰写；定期做 Keep/Delete 扫描，不确定的先标记、确定过期的删除。
- **示例**：每个版本发布时顺手删掉已过期的“旧路径说明”，并在新文档里链接到权威规范。
- **反例**：仓库里同时存在 3 份内容矛盾的“使用说明”，且都未标注 deprecated。
- **来源**：R34-8、R34-9、R34-11。
