# dev-testing · 测试调试（已蒸馏）

> 定位：测试是对**公开行为**的契约，不是对内部实现的合影。覆盖率是参考，不是完成标准。
> 原则：每个测试必须能变红，锁对外可观测行为；调试先做最小复现，再二分定位。

## 触发条件

- 用户要写单元/集成/E2E 测试、设计测试夹具、评估覆盖、修复 flaky。
- 遇到“偶现失败”“本地过了 CI 挂了”“很难复现”的调试问题。
- 需要判断“这个模块该测什么、怎么测才有效”。

## 核心动作

### 1. 测试分层与选择

- 单元测试：纯逻辑/算法/核心规则，快、确定、内存小。
- 集成测试：跨模块/真实数据库/外部服务通过测试替身或少样本真实依赖。
- E2E 测试：用户关键旅程，数量少、慢、易 flaky，只保关键路径。
- 按风险分配：核心规则多测；装饰/外部展示少测；不要追求所有分支覆盖率。

> 边界：测试金字塔是实践参考，不是铁律；先看行为契约在哪层最容易锁住。

### 2. 测试公开接口

- 测试通过公开 API/CLI/组件 props 触发，不依赖私有函数、内部 state、DOM 细节。
- 断言可观测结果（返回值、输出、状态变更、副作用），不测“是否调用了某内部方法”。
- 每个测试必须先见失败（可证伪），再修绿；否则测试可能是无效的。
- 命名表达行为：`test('用户输入非法时返回 400')`，而不是 `test('function x')`。

> 边界：为了测试加 getter/setter 暴露内部状态，是坏味道；应重构接口而非穿透。

### 3. 夹具、隔离与确定性

- 每个测试独立数据，不依赖执行顺序；用 setup/teardown 清理。
- 时间/随机数/网络/文件系统注入 fake 或固定种子，保证确定性。
- 外部依赖用契约测试或测试替身；不要直接连生产服务。
- 测试数据要小且能快速失败；避免超大 fixture 掩盖问题。

### 4. Flaky 治理

- 先稳定复现：记录失败日志、环境、随机种子、执行顺序。
- 常见原因：共享状态、时间依赖、并发/顺序依赖、外部网络、资源限制、未清理资源。
- 修复后不能只“重跑过了”；要解释根因，并加确定性防护。
- 对慢/不稳定测试做隔离或标记；不要让 flaky 污染主流水线。

### 5. 调试最小复现

- 先拿最小可复现用例：删除无关代码、固定输入、固定并发/顺序、抓完整日志。
- 二分定位：注释/拆分/打印/断点/日志逐步缩小范围。
- 区分环境差异：本地 vs CI、版本、依赖、并发、时区、数据。
- 修 bug 后补回归测试，确保同一问题不会再进来。

## 反例 / 边界

| 反例 | 正确做法 |
|---|---|
| “覆盖率 100% 就完成了” | 覆盖率是信号；要看测试是否锁住行为、能变红 |
| “测试写很多但没有断言” | 每个测试必须有明确可观测断言 |
| “测试调用私有方法省事” | 测试公开接口；私有逻辑通过公开行为验证 |
| “flaky 就重跑一下” | 找根因 + 确定性防护；否则风险仍在 |
| “遇到 bug 直接改代码不写复现” | 先最小复现，再加回归测试 |

## 2026 深度补强（Round 32）

> 本轮新增 8 条可执行规则，重点补齐：测试尺寸分级、跨层去重、数据库隔离策略、容器化真实依赖、flaky 治理流水线、随机顺序门禁、单 Act 测试与 E2E 数量门禁。参考：Ham Vocke《The Practical Test Pyramid》、SWE at Google Ch11、pytest-django、Testcontainers、Microsoft Learn、Google Testing Blog。

### 1. 用“测试尺寸”而非名字做分类

- 按资源与确定性分级：**Small** = 单进程、无阻塞 I/O（无真实网络/磁盘/时钟）；**Medium** = 单机、可访问 localhost；**Large** = 跨机器。
- 问自己：“这个测试能跑多快、多确定？”比叫它“单元/集成”更诚实。
- 示例：需要真实数据库的测试至少是 Medium；要把它保持 Small，就用 in-memory/test double，并把“真实依赖交互”留给 Medium 层。
- 反例：把“连了真实 DB 的类”称为“单元测试”，于是没人按集成测试治理它，CI 慢且偶发失败长期存在。

### 2. 同一条行为不要三层重复

- 单元层锁纯逻辑；集成层锁接线/契约/持久化；E2E 只锁关键用户旅程。
- 示例：Unit 已断言 `discount(100)=90`；Integration 应断言“DAO 正确写入 discount 字段”；E2E 应断言“用户下单后账单页显示 90 元”。不要三层都写同一数值断言。
- 反例：同一断言在 unit/integration/e2e 各抄一遍，小改动要改三个地方，且慢层失败无法判断是哪层逻辑坏。

### 3. 数据库隔离三选一（按测试目标选）

- **事务回滚**：每个测试在事务内跑、结束回滚（pytest-django 默认、Spring `@Transactional`）——最快，但测不了真正的 commit/事务边界。
- **唯一命名空间**：随机租户/随机库/唯一 key 前缀，支持并行；断言不假设固定 `id=1`。
- **一次性容器**：Testcontainers 等为每个流水线/套件起真实依赖，避免共享开发库与跨流水线数据污染。
- 反例：所有测试连同一个开发数据库，靠“先清理再跑”或约定顺序；并行流水线必然互相污染，本地与 CI 结果不一致。

### 4. 真实依赖用一次性容器 + 就绪等待

- 集成测试要真数据库/消息队列时，用容器在测试代码里按需启动，不要预配共享环境。
- 启动后等“就绪”：用 wait strategy / healthcheck / 端口探测；不要裸 `sleep(5)`（固定延时既慢又不稳）。
- Testcontainers 会把容器端口映射到随机 host 端口，测试代码读运行时端口，不要写死 5432/3306。
- 反例：测试里 `Thread.sleep(3)` 等 DB 起来；CI 机器慢时仍连不上报“连接被拒”，本地快时又通过。

### 5. Flaky 治理流水线（探测→隔离→归因→修复→防复发）

- **探测**：CI 对每次失败记录完整日志、随机种子、环境、执行顺序；用“重跑是否稳定变绿”做初步分类。
- **隔离**：确认 flaky 后立即打标记/隔离（`@flaky`、quarantine runner、独立 job），开 issue 并指定 owner；不要让 flaky 阻塞主分支。
- **归因**：按根因清单排查（共享状态、时间依赖、并发/顺序、外部网络、资源限制、未清理资源）。
- **修复**：根治后解除隔离并保留确定性防护；重试只作为调查期的临时缓解，不能长期当修复。
- **量化**：10,000 个测试每天跑、每个测试 0.1% 概率误报时，每天约 10 次假警报；flaky 率是 suite 健康度指标，需监控趋势。

### 6. 随机化测试顺序 + hermetic 原则

- 每个测试应自带 setup/execute/teardown 所需信息，不假设外部环境（共享 DB、固定执行顺序、已存在的全局 state）。
- 在 CI 用随机顺序/洗牌运行（pytest-randomly、JUnit 随机 order），让隐藏的顺序依赖在合并前暴露。
- 反例：“本地全绿、CI 偶红”，检查发现测试依赖前一个测试创建的数据；随机顺序后立刻暴露。

### 7. 一个测试只做一件事（一个 Act + 最小输入）

- 一个测试只包含一个 Act，避免多个行为交叉；若第一个断言失败，后续无法判断哪一步坏。
- 输入保持最小：只给触发当前行为所需的参数；不要把完整生产数据/大 fixture 当默认输入。
- 对硬编码魔法值用命名常量表达意图（如 `MAXIMUM_RESULT = "1001"`），失败信息更像规格说明而不是实现细节。
- 反例：一个测试里 login → create order → assert three things；失败后只能靠读代码猜是哪一步坏了。

### 8. 测试金字塔反向与 E2E 数量门禁

- 若大部分行为只在 E2E 验证，unit/integration 空白，CI 会慢且失败难定位。
- 用“能下沉就下沉”原则：先把断言尽量放到最小可锁层，再在高层只补接线/旅程。
- 给 E2E 设数量/时长预算：例如主流水线 E2E 控制在个位数～几十个、几分钟内；超出就转 nightly/独立 job。
- 反例：每加一个页面都写一个完整浏览器 E2E，套件从 5 分钟膨胀到 40 分钟，开发反馈循环被破坏。
