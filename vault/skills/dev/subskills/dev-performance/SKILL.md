# dev-performance · 性能优化（已蒸馏）

> 定位：性能问题的第一原则是**测量**。没有基线就没有优化，没有可复现用例就没有结论。
> 本子技能提供定位-分类-优先级-回归的通用方法。

## 触发条件

- 用户说“很卡 / 很慢 / 内存高 / 包大 / 数据库慢”。
- 需要做性能优化、性能评审、性能回归测试。
- 需要判断“这个性能优化值不值得做”。

## 核心动作

### 1. 建立测量与基线

- 定义指标：延迟（p50/p95/p99）、吞吐（QPS/RPS）、内存/CPU、包体、加载时间、错误率。
- 在**真实环境或可复现测试环境**采集基线；记录机器/数据规模/版本。
- 用 profiler（CPU、内存、网络、渲染）而不是猜热点。
- 优化前后同环境、同负载对比，至少 3 次。

> 边界：开发机上的秒级优化不等于生产提升；网络/DB 等外部因素必须纳入。

### 2. 热点定位与瓶颈分类

- 按“从用户到系统”分层：客户端渲染 → 网络 → 服务端 CPU/IO → 数据库/缓存 → 第三方。
- 先找数量级最大的项：一个慢 SQL 或大图/大 bundle 通常比循环微优化有效得多。
- 用火焰图/调用链/性能面板看耗时分布，而不是凭代码直觉。
- 数据库慢查询看执行计划、索引、N+1；接口慢看是否存在串行等待。

### 3. 优化优先级

- 网络与加载：压缩、HTTP/2、缓存、CDN、懒加载、关键路径优化。
- 渲染：减少重排/重绘、避免大列表全量渲染、虚拟化、减少 JS 主线程长任务。
- 内存：找泄漏（长生命周期引用、未清理定时器/监听）、减少大对象复制，防止 GC 抖动。
- 服务端：缓存热数据、异步/批处理、连接池、减少锁竞争。
- 包体：tree-shaking、代码分割、按需加载、移除重复依赖。

> 边界：优化按“可观测影响”排序，不做无证据的微优化；不要牺牲接口/可维护性除非有明确数据。

### 4. 缓存与预计算的适用边界

- 缓存用于读多写少、可容忍一定过期、可失效的数据。
- 必须设计缓存键、TTL、失效/淘汰策略；防止缓存雪崩/穿透。
- 预计算适合低频变但高频算的场景；要给出更新路径与一致性边界。
- “加缓存”不是万能：写放大、内存成本、一致性风险都要评估。

> 边界：金融/强一致场景不能无脑缓存；用缓存前明确数据一致性要求。

### 5. 性能回归落地

- 将关键指标做成自动化测试/基准，设阈值；跑不动就不算完整。
- 优化提交附上优化前后对比数据（baseline/after），并保留可复现脚本。
- CI 中放轻量性能冒烟（如 bundle 大小、关键接口延迟），重基准跑在独立环境。

## 反例 / 边界

| 反例 | 正确做法 |
|---|---|
| “先改成多线程再说” | 先测热点；若是 IO 等待，多线程也许有效；若是 CPU 瓶颈，多线程未必 |
| “把循环里的 if 优化一下” | 先看 profiler；局部微优化通常占比很小 |
| “直接加缓存” | 明确读多写少、TTL、失效，并评估一致性成本 |
| “优化完跑一次就宣布提升” | 至少 3 次，同环境同负载，报告 p95 等指标 |
| “只看 CPU 高不高” | 延迟/吞吐/错误率/内存都要看 |

## 2026 深度补强（Round 32）

> 本轮聚焦：性能预算工程化、现场/实验室数据分工、LCP/INP 可执行手段、内存快照排查、SQL 执行计划证据链、后端等待分解、可稳定复用的回归护栏。

### 规则 1：性能预算要变成“可断言数字 + 分资产/分路由”，而不是一句口号

- 为 LCP、INP、CLS、JS/bundle 体积、首屏图片与字体开销分别设预算；不同页面（核心交易页 vs 长尾营销页）预算不同。
- 在 CI 用 Lighthouse budget.json 或等价工具把预算变成失败条件；预算调整必须带数据依据，并在 PR 中说明。
- 预算随产品阶段演进：先用 RUM/CrUX 现场分布校准，再决定“严格卡”还是“容忍”。

> 反例：只有一个“全站 < 3s”预算，出问题时无法定位是哪个页面/哪类资产超支。

### 规则 2：现场（RUM）与实验室（Lighthouse）数据分工；INP 看现场分布而非平均

- 实验室数据用于开发期快速回归，现场数据（CrUX/RUM）用于对外承诺与监控；两者不能互相替代。
- INP 按交互事件测量：≤200ms 良好、200–500ms 需改进、>500ms 差；看 p75 分布，不要只看平均值。
- 拆解交互延迟 = 输入延迟 + 处理时间 + 呈现延迟；优先消除事件处理里的同步重算、强制布局（layout thrash）与长任务，而不是简单堆 `defer`。
- 示例：click 里做全量列表过滤 → 先更新视觉、把计算放 `requestIdleCallback`/`scheduler.yield()`，或改成增量/虚拟列表。

### 规则 3：LCP 优化先看“谁在挡路”，用 preload/fetchpriority，不要盲目 lazy

- LCP 元素若为图片：`fetchpriority="high"` + 预加载 LCP 资源；**不要**给 LCP 图片加 `loading="lazy"`。
- 若是 TTFB 高，先解决后端/网络/缓存（收益通常大于压图）；若是字体阻塞，用 `font-display: swap` 并预加载 woff2。
- 记录 LCP 分解（TTFB → 资源加载 → 渲染），把优化资源投到最大一项，而不是平均用力。

> 反例：把所有图片都 `lazy`，结果首屏主图反而更慢；优化半天 CSS 却发现 LCP 瓶颈在 TTFB。

### 规则 4：内存排查用“快照对比 + retained size + 分离 DOM”，不要只盯着 RSS

- 触发同一路径 2–3 次，操作前后各取堆快照；比较三个快照间新增对象与 retained size，分离 DOM 节点（detached DOM）是泄漏高频信号。
- 长生命周期对象持有 DOM/监听器/定时器是根因；缓存优先 `WeakMap`/`WeakRef` 或设置容量上限与淘汰策略。
- 内存路径应“重复执行后看趋势”：每次操作后内存回落再缓慢上升=健康；持续上升=泄漏。

> 示例：全局数组无限 push 埋点日志 → 改为有界环形 buffer 或定期批量归档；否则内存随时间线性增长。

### 规则 5：SQL 优化以 EXPLAIN ANALYZE 的“实际行为”为准，不猜“它应该走索引”

- 先看 `actual rows` vs `estimated rows`：差距大说明统计信息旧或参数化计划退化，先 `ANALYZE`/更新统计，再谈加索引。
- 优先覆盖索引（covering / index-only scan）让查询列全部从索引取，避免 `SELECT *` 回表放大；索引是否被用于过滤、排序、覆盖要在计划里确认。
- `ORDER BY` / `GROUP BY` 也可能吃索引；对索引列做函数、隐式类型转换、前缀模糊匹配会破坏索引可用性。
- 反例：慢查询就加索引，但计划仍显示 Seq Scan + 低选择性/高回表；应先看计划里 actual rows 与访问方法。

### 规则 6：后端瓶颈用 span/调用链拆“等待”与“计算”，并纳入饱和度指标

- 一个接口慢，先看 trace 里时间花在 CPU、数据库、外部调用还是队列/锁等待；等待占大头时“加更多线程/机器”可能无效。
- 用 golden signals：流量、错误、延迟、饱和度（队列深度、CPU 使用、连接池使用率）；只盯 CPU 会漏掉排队型饱和。
- 连接池大小不是越大越好：以“池等待时间≈0 且线程/连接不过剩”为目标，按核心数、IO 并发与测量标定；连接池排队是数据库慢的直接信号。
- 示例：接口 P99 高但 CPU 低 → 大概率在 DB 连接池/工作队列排队，优化循环内代码收益很小。

### 规则 7：性能回归护栏要“稳”：多次采样、暖机、看趋势、预算留噪声余量

- 共享 CI runner 上性能易抖动：至少 3–5 次采样取 p50/p95，重基准放固定机器/独立环境；不要用单次结果判红。
- 预算设噪声余量；主检查看“趋势回退”而非“精确超 1ms 就挂”；轻量冒烟进 CI，重基准定时跑。
- 性能 PR 必须附 baseline/after 与复现命令；阈值调整要记录原因，防止“为过 CI 悄悄放宽预算”。
