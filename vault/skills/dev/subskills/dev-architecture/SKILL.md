# dev-architecture · 系统设计/分布式（已蒸馏）

> 定位：给 dev 模块提供“系统级/分布式决策”的最小可执行集。**只回答“系统层怎么选型、怎么拆分、怎么权衡”**
> 不重复 dev-backend 的 API/数据模型/错误语义、dev-concurrency 的锁/原语、dev-performance 的测量/优化、
> dev-ops-sre 的部署/监控/回滚、dev-testing 的测试/调试。

## 触发条件

- 用户要设计或评审**一个系统/一组服务**的顶层架构：需求 → 约束 → 接口 → 数据流。
- 需要决定**是否拆服务、按什么边界拆、每个服务拥有什么数据与职责**。
- 需要做**消息/队列选型**：直连还是队列、至少一次/至多一次/精确一次、幂等、顺序、DLQ、背压。
- 需要选择**一致性模型**：强一致/最终一致、读写己见、事务边界、Saga/Outbox/补偿。
- 需要做**容量估算**：QPS、延迟预算、存储增长、带宽的粗略数量级判断。

## 不应触发 / 路由边界

| 用户问题 | 应路由 |
|---|---|
| 实现 REST/GraphQL/RPC 接口、数据库表/迁移、错误码、鉴权、单服务分层 | `dev-backend` |
| 线程/进程/协程、锁、原子性、竞态、死锁、异步模型 | `dev-concurrency` |
| 慢查询/内存/包体/渲染、热点定位、缓存/性能回归 | `dev-performance` |
| 发布流水线、容器、监控告警、on-call、回滚 | `dev-ops-sre` |
| 测试分层、flaky、调试最小复现 | `dev-testing` |

## 反例（不应触发 dev-architecture）

- ❌ “这个 REST 接口错误码怎么设计？” → dev-backend。
- ❌ “这段代码会不会死锁？” → dev-concurrency。
- ❌ “首页加载慢怎么优化？” → dev-performance。
- ❌ “CI/CD 怎么配？” → dev-ops-sre。
- ❌ “这个 bug 怎么复现？” → dev-testing。

## 正确触发示例

- ✅ “这个系统要不要拆成两个服务？拆完消息怎么传？”
- ✅ “订单创建跨多个服务，怎么保证最终一致？”
- ✅ “高峰期预估 10 万 QPS，服务节点和存储大概要多少？”
- ✅ “这个团队边界/领域边界怎么定，数据归谁所有？”

## 系统设计与服务拆分

> 触发：设计/评审一个系统或一组服务的顶层架构，或决策“要不要拆服务”。
> 本节只回答系统级取舍；接口实现细节（REST 字段、数据库 DDL、鉴权中间件）交给 `dev-backend`。

### 1. 需求 → 约束 → 接口 → 数据流（检查清单）

- **需求**：先写功能需求与**非功能需求**（可用性、延迟、吞吐、一致性、成本、合规）；明确“本期不做什么”。
- **约束**：列出技术栈/团队/运维/预算/既有系统接口/合规约束；没有约束的架构方案无法评估。
- **接口**：先定对外/对内接口契约——输入、输出、错误、幂等、版本；能机器可读就机器可读（OpenAPI/proto/JSON Schema）。
- **数据流**：画主链路：请求 → 服务 → 存储/外部依赖；标出同步/异步、读放大/写放大、故障点、依赖顺序。
- **验证**：1 页架构图 + 接口表 + 每个关键路径的可用性/延迟/容量目标；讲不出目标的设计还停留在想法。

> 边界：一次性脚本/单机小工具可跳过；只要会被多个团队/多年维护，就应至少写出接口与数据流。

### 2. 服务拆分判据（内聚 / 耦合 / 所有权 / 故障隔离）

| 判据 | 检查问题 | 边界 |
|---|---|---|
| **内聚** | 这个服务能否用一句话解释一个完整业务能力？同一数据生命周期是否在一个边界内？ | 拆完后需要跨服务做分布式事务才能维持不变量 → 说明内聚边界选错了 |
| **耦合** | 跨服务依赖是否单向、低频、可降级？ | 如果拆完仍需频繁跨服务 join/同步调用，先别拆 |
| **所有权** | 每个数据/领域是否有唯一写所有者（single writer）？ | 多个服务直接写同一张表 = 所有权缺失，是坏拆分 |
| **故障隔离** | 拆开是否带来独立部署/独立扩缩容/更小爆炸半径？ | 若只是“代码文件多”，没有独立故障域，拆微服务收益不足 |

### 3. 先单体后微服务（monolith-first）

- 在业务边界不清、团队小、并发/发布频率不高时，**先做模块化单体**：清晰模块边界 + 单进程部署。
- 拆分前先回答：拆出来的服务是否**独立演进、独立扩缩容、独立故障**；若都答“否”，不是拆服务的时候。
- 拆分不是技术栈不同的理由；同一业务能力因“想用新语言”而拆，通常增加运维成本而非收益。

> 边界：微服务/分布式不是目标；目标是**可维护性、可扩展性与故障隔离**。没有可测量的收益就不拆。

### 反例

| 反例 | 正确做法 |
|---|---|
| “订单服务直接写库存服务的表” | 库存表只由库存服务拥有；订单通过接口/领域事件同步 |
| “为了微服务而拆成 10 个服务，共用一个数据库” | 先模块化单体；等出现独立所有权/独立扩缩容需求再拆 |
| “接口还没定，先搭服务骨架” | 先定接口契约与数据流图，再实现 |
| “一个团队负责所有服务，却要求每个服务独立部署” | 所有权要与团队边界对齐；无所有权就没有可维护的微服务 |

## 消息队列与异步

> 触发：需要选择“同步直连还是队列”、设计消息投递可靠性、处理消费失败/积压。
> 本节落地到“架构选型与可靠性动作”；线程/协程/锁/并发测量不在这里展开（交给 `dev-concurrency`），性能剖析交给 `dev-performance`。

### 1. 直连 vs 队列决策表

| 场景 | 选择 | 理由 |
|---|---|---|
| 调用方必须立刻拿到结果，失败重试简单 | 直连/同步 RPC | 简单、延迟可预测、无额外中间件 |
| 需要削峰、解耦、多消费者、异步长任务 | 队列 | 缓冲 + 解耦 + 独立扩缩容 |
| 业务写库与发消息必须一起成功 | 事务性消息 / Outbox | 避免“库成功了消息没发” |
| 主链路对延迟敏感，慢任务可以异步 | 队列 + worker | 不阻塞主请求 |
| 消息量小、强一致、无削峰需求 | 直连/本地事务 | 避免引入分布式复杂度 |

> 边界：队列不是“用了就自动解耦”；它引入延迟、重复、乱序、积压与运维成本。没有明确收益时先用直连。

### 2. 投递语义

- **at-most-once**：可能丢消息、不重复；适合可容忍丢失、可全量重建的场景。
- **at-least-once**：可能重复、不丢；是多数队列默认/现实语义，**消费端必须幂等**。
- **exactly-once**：由 broker + producer + consumer + 存储共同保证；若无法端到端保证，就用“幂等消费 + 去重”达到**效果上的精确一次**。

> 边界：不要口头宣称“精确一次”；要说明由哪一层、用什么机制保证，以及失败时退化成哪种语义。

### 3. 幂等

- 消费者用**业务唯一键**（orderId / eventId / idempotencyKey）做去重：唯一约束、幂等表、或原子“检查+写入”。
- 处理成功后记录本次消费结果，重放时不再产生二次副作用。
- 幂等必须对**并发重复**与**重试重复**都安全，不能只检查“是否已处理过”再非原子更新。

### 4. 顺序

- **单分区/单队列**内保序；多消费者并行消费会打乱全局顺序。
- 需要顺序时按业务键路由到同一分区（同一 orderId 同一分区），而不是要求全局总序。
- 乱序可容忍时，用版本号/seq 比较或“最终一次写入”兜底。

> 边界：全局强顺序成本高、吞吐损失大；只在业务真正依赖时才做。

### 5. DLQ 与背压

- 消费失败分类：瞬时错误 → 重试 + 指数退避；永久错误 → 投递死信队列（DLQ）。
- DLQ 必须有人工/自动处理与告警，不能无限堆积；处理完要能回放或对账。
- 背压/积压：要看到队列长度、消费延迟、失败率；消费端限流，必要时降级/丢弃有明确策略。
- 没有监控的队列是黑盒：至少记录积压深度、处理耗时、重试/死信计数。

> 边界：具体线程池大小、锁、剖析与调优交 `dev-concurrency` / `dev-performance`；这里只管消息系统的架构级可靠性动作。

### 反例

| 反例 | 正确做法 |
|---|---|
| “用了队列就不用管失败” | 定义重试策略、DLQ、告警与对账 |
| “发消息成功 = 业务成功” | 业务事务与消息发送要原子（Outbox/事务消息） |
| “必须全局顺序消费” | 确认是否真需要；通常按业务键保序即可 |
| “队列积压就加消费者” | 先看消费瓶颈与下游压力；无限制加机器可能打垮下游 |

## 一致性模型

> 触发：需要选择一致性级别、定义事务/跨服务数据不变量，或设计 Saga/Outbox/补偿。
> 本节只处理“分布式系统层的一致性取舍”；单机内的锁、原子变量、线程同步交给 `dev-concurrency`。

### 1. 一致性模型选择表

| 模型 | 含义 | 适用 | 代价 |
|---|---|---|---|
| 强一致（线性一致性） | 读到的总是最近一次写 | 余额扣减、库存扣减、唯一性约束 | 可用性/延迟受分区与多数派约束 |
| 读写己见（read-your-writes） | 用户写后能立刻读到自己的写 | 个人资料、会话类场景 | 需要会话粘性/因果路由 |
| 单调读（monotonic reads） | 不会再读到更旧的版本 | 多副本读、论坛/通知 | 需要副本版本协调 |
| 最终一致（eventual consistency） | 最终会收敛，期间可能读到旧值 | 统计、推荐、通知、缓存 | 需要业务容忍 + 补偿/对账 |

> 边界：一致性不是“越强越好”；强一致降低可用性与延迟容量。每个接口/数据都要单独声明级别。

### 2. CAP 取舍（实际是分区下的取舍）

- 分布式系统必然面对网络分区；**分区时**要在“一致性”与“可用性”之间为每个操作做选择。
- CP 系统（如多数派复制）分区时可能拒绝服务，以保证不返回旧数据。
- AP 系统（如多主/最终一致）分区时仍可用，但可能返回旧数据/冲突；合并策略必须设计。
- 不要用“CAP 只能三选二”当借口；先明确业务对“返回旧值” vs “暂时不可用”的容忍度。

> 边界：CAP 描述的是分区时刻；非分区时强一致和可用性可以同时满足。

### 3. 事务边界与跨服务模式

- **本地事务**：一个写操作尽量落在一个服务、一个数据库事务内；事务内不做远程调用，避免长事务。
- **Saga**：把跨服务流程拆成多个本地事务步骤，每步可提交；失败时执行**补偿动作**回滚前面步骤。
- **Outbox**：业务写与发消息在同一本地事务：先写业务表 + outbox 表，再由发布器异步投递；消费者幂等。
- **补偿**：对已提交的前序步骤做反向操作（退款、释放库存、撤销积分）。

| 模式 | 失效条件 / 必须设计 |
|---|---|
| Saga | 补偿动作可能本身失败；没有全局原子回滚；每步必须幂等、可重试、可对账 |
| Outbox | 发布器可能重复投递，消费者必须幂等；outbox 清理与投递状态要有监控 |
| 补偿 | 对外不可逆动作（已发邮件/已通知）不能简单“撤销”，需要显式取消流程或对账 |

### 4. 冲突处理

- 多写/最终一致场景要定义冲突解决：版本号/LWW、合并、人工仲裁、CRDT。
- 每个数据变更要带版本/时间戳/因果信息，不能只靠“最后到达者胜”而不检查业务不变量。
- 对账/重放是分布式一致性的必要兜底，不是可选项。

> 边界：冲突解决不是万能；先尝试缩小写冲突面（单写者、按业务键路由），再用合并策略兜底。

### 反例

| 反例 | 正确做法 |
|---|---|
| “跨服务用两阶段提交保证强一致” | 评估 2PC 的可用性/锁成本；多数业务用 Saga + 补偿 + 对账 |
| “先发消息再写库，失败了补发” | 用 Outbox/事务消息，让业务写与消息发送原子 |
| “最终一致就完全不用管” | 必须有收敛规则、冲突合并、补偿/对账与监控 |
| “分布式事务失败就整个回滚” | Saga 没有全局回滚，只能逐步骤补偿；补偿也要幂等 |

## 容量估算

> 触发：在做架构设计/扩容/存储选型前，需要“数量级上够不够”的粗略判断。
> 本节给出的是**粗略估算（back-of-envelope）**；真实容量与延迟必须靠压测/观测，交给 `dev-performance`。

### 1. 估算步骤

1. **定峰值与平均**：写清楚日活/峰值 QPS、读写比例、单请求内部调用倍数（一个用户请求可能打 N 个下游）。
2. **算单请求资源**：估计单请求 CPU 时间、内存、IO 次数；按语言/框架/缓存命中率留余量。
3. **定延迟预算**：端到端 p99 = 网络 + 服务排队 + 处理 + 下游调用 + 重试；不要只看平均值。
4. **算存储增长**：`日新增行 × 行大小 × 保留天数 × 副本数 × 索引/日志放大系数`。
5. **算带宽**：`QPS × 平均响应大小` + 内部消息/日志/备份流量。

### 2. 常用粗略公式

```text
单实例处理能力(理论) = 1000ms / 单请求CPU时间(ms)
所需实例数 ≈ 峰值QPS / (单实例处理能力 × 负载安全系数(建议 ≤0.5-0.7)) + 冗余实例
年存储增量 ≈ 写QPS × 86400 × 365 × 单行大小 × 副本数 × 放大系数
峰值带宽 ≈ (读QPS × 平均响应大小 + 写QPS × 平均请求大小) × 安全系数
```

### 3. 可复算示例

- 场景：峰值 **1,000 QPS**；读 80%、写 20%；单请求核心 CPU 约 5ms；单行 1KB；保留 1 年；3 副本。
- 实例估算：
  - 单核理论 `1000ms / 5ms = 200 QPS`
  - 留 50% 负载余量 → 单实例约 `100 QPS`
  - `1000 / 100 = 10` 个实例；加 2 个冗余 → **约 12 个实例**
- 存储估算：
  - 写 QPS `1000 × 20% = 200/s`
  - 年写入 `200 × 86400 × 365 × 1KB ≈ 6.3 TB`
  - 3 副本 `≈ 18.9 TB`；索引/日志余量 ×1.5 → **约 28 TB/年**
- 结论：这只是数量级估计；必须用真实数据修正，并跑压测确认。

### 4. 与 dev-performance 的边界

- 容量估算是**设计前的数量级判断**，用于选架构/节点/存储。
- 一旦进入“实测延迟、热点定位、优化后是否有提升”，交给 `dev-performance`。
- 估算里出现的假设（每请求 5ms、行大小 1KB）必须标注为假设，不能当测量值。

### 反例

| 反例 | 正确做法 |
|---|---|
| “估算 12 个实例就够了，不用压测” | 估算只给起点；上线前用真实负载压测/容量测试验证 |
| “只看平均 QPS，不看峰值” | 至少同时看峰值与 p99；流量尖峰决定容量 |
| “存储按主库单副本算” | 副本、索引、日志、备份都会放大存储 |
| “容量不够就加机器” | 先看瓶颈是 CPU/内存/IO/网络/下游；盲目扩容可能只增加成本 |
