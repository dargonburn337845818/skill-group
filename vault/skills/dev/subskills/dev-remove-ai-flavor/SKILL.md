# dev-remove-ai-flavor · 去 AI 味（已蒸馏）

> 定位：去 AI 味不是“删除形容词/加表情”，而是**把空泛、堆砌、无主语的模板化表达改成具体、可验证、有人称的短句**。
> 优先级：技术准确性 > 可维护性 > 人味。

## 触发条件

- 用户说“这段话太 AI 了 / 像机器写的 / 帮我改成人话”。
- 代码注释、README、PR、UI 文案、消息回复中出现空泛总结、过度礼貌、万能套话。
- dev 模块命中“AI 风格审查与去 AI 味”时；或 writing 的 copywriting 需要做改写审查时。

## 核心动作

### 1. 识别常见 AI 味模式

| 模式 | 例子 |
|---|---|
| 空泛开场 | “在当今快速发展的时代”“随着技术的进步……” |
| 万能套话 | “赋能”“闭环”“抓手”“颗粒度”“底层逻辑”“价值最大化” |
| 过度总结 | “综上所述”“总而言之”“不难发现”“众所周知” |
| 无主语/被动堆砌 | “本方案被设计用来……” |
| 排比但无信息 | “首先……其次……再次……最后……” |
| 过度客气 | “非常荣幸”“深感荣幸”“希望您能……” |
| 空洞承诺 | “显著提升”“业界领先”却无数据 |

### 2. 改写原则

- **具体 > 抽象**：把形容词换成数字、动作、结果；“很快”改“从 8 秒降到 1 秒”。
- **结论先行**：每段第一句说结论/动作，不先铺垫。
- **有人称**：用“你/我们/用户”，少用无主句；“系统会自动……”改成“你运行 `make` 后会自动……”。
- **短句为主**：一句一个动作；删除不承载信息的连接词。
- **保留技术细节**：算法名、命令、参数、限制、警告不能为了“像人”而删。

### 3. 验证改写是否成功

- [ ] 信息是否丢失？把原文与改写版并排，逐条比对事实/命令/数字/引用。
- [ ] 语气是否一致？文档/UI/代码注释要分别匹配文体，不是统一“活泼”。
- [ ] 是否仍有空泛词？搜索“赋能/闭环/综上所述/值得注意的是”等。
- [ ] 可读性是否提升？30 秒内能不能抓到要点。
- [ ] 是否引入含糊承诺？没有数据支撑的“更好/更强”要改成具体或删除。

### 4. 分场景处理

- **代码注释**：解释“为什么”和边界，不重复代码本身；删“This function is used to……”只留关键意图。
- **文档/README**：先写“做什么—怎么跑—哪里求助”，用具体命令和示例。
- **UI 文案**：短句、动词开头、给用户下一步；不用“您的请求已成功处理”，改“已保存”。
- **PR/发布说明**：列变化 + 影响 + 迁移方式，不写“本次更新优化了用户体验”。

## 反例 / 边界

| 反例 | 正确做法 |
|---|---|
| “删除所有形容词和连接词” | 形容词/连接词有信息承载；只删空洞的，保留必要的 |
| “更像人=加语气词/表情” | 人味来自具体与真诚，不是表情符号 |
| “把专业术语改成大白话” | 面向开发者保留术语；面向用户才翻译，且不能失真 |
| “为了流畅省略边界条件” | 错误处理/限制必须保留；宁可慢一点也要准确 |
| “套用某位作者的文风” | 文体风格是分支，不是普适规则；以读者理解为准 |
