# dev-remove-ai-flavor · 去 AI 味（已蒸馏）

> 定位：去 AI 味不是“删除形容词/加表情”，而是**把空泛、堆砌、无主语的模板化表达改成具体、可验证、有人称的短句**。
> 优先级：技术准确性 > 可维护性 > 人味。

## 触发条件

- 用户说“这段话太 AI 了 / 像机器写的 / 帮我改成人话”。
- 代码注释、README、PR、UI 文案、消息回复中出现空泛总结、过度礼貌、万能套话。
- dev 模块命中“AI 风格审查与去 AI 味”时；或 writing 的 copywriting 需要做改写审查时。

## 核心动作

### 1. 识别常见 AI 味模式

| 模式 | 例子 |
|---|---|
| 空泛开场 | “在当今快速发展的时代”“随着技术的进步……” |
| 万能套话 | “赋能”“闭环”“抓手”“颗粒度”“底层逻辑”“价值最大化” |
| 过度总结 | “综上所述”“总而言之”“不难发现”“众所周知” |
| 无主语/被动堆砌 | “本方案被设计用来……” |
| 排比但无信息 | “首先……其次……再次……最后……” |
| 过度客气 | “非常荣幸”“深感荣幸”“希望您能……” |
| 空洞承诺 | “显著提升”“业界领先”却无数据 |

### 2. 改写原则

- **具体 > 抽象**：把形容词换成数字、动作、结果；“很快”改“从 8 秒降到 1 秒”。
- **结论先行**：每段第一句说结论/动作，不先铺垫。
- **有人称**：用“你/我们/用户”，少用无主句；“系统会自动……”改成“你运行 `make` 后会自动……”。
- **短句为主**：一句一个动作；删除不承载信息的连接词。
- **保留技术细节**：算法名、命令、参数、限制、警告不能为了“像人”而删。

### 3. 验证改写是否成功

- [ ] 信息是否丢失？把原文与改写版并排，逐条比对事实/命令/数字/引用。
- [ ] 语气是否一致？文档/UI/代码注释要分别匹配文体，不是统一“活泼”。
- [ ] 是否仍有空泛词？搜索“赋能/闭环/综上所述/值得注意的是”等。
- [ ] 可读性是否提升？30 秒内能不能抓到要点。
- [ ] 是否引入含糊承诺？没有数据支撑的“更好/更强”要改成具体或删除。

### 4. 分场景处理

- **代码注释**：解释“为什么”和边界，不重复代码本身；删“This function is used to……”只留关键意图。
- **文档/README**：先写“做什么—怎么跑—哪里求助”，用具体命令和示例。
- **UI 文案**：短句、动词开头、给用户下一步；不用“您的请求已成功处理”，改“已保存”。
- **PR/发布说明**：列变化 + 影响 + 迁移方式，不写“本次更新优化了用户体验”。

## 反例 / 边界

| 反例 | 正确做法 |
|---|---|
| “删除所有形容词和连接词” | 形容词/连接词有信息承载；只删空洞的，保留必要的 |
| “更像人=加语气词/表情” | 人味来自具体与真诚，不是表情符号 |
| “把专业术语改成大白话” | 面向开发者保留术语；面向用户才翻译，且不能失真 |
| “为了流畅省略边界条件” | 错误处理/限制必须保留；宁可慢一点也要准确 |
| “套用某位作者的文风” | 文体风格是分支，不是普适规则；以读者理解为准 |

## 2026 深度补强（Round 32）

> 本轮补齐“表面擦完仍像 AI”的部分：机器残留、结构把戏、无源权威、中文翻译腔、表演式人味，并把验证从“读一遍”升级为可测量检查。

### 1. 先清机器残留与排版指纹（成本最低、命中率最高）

AI 腔不只来自用词，还来自“人不会按出的字符/格式”。先把这类确定性残留清掉：

- **破折号密度**：`—` / `——` 一段出现 2 次以上即可疑。按它实际干的活替换：硬停→句号；引出结论→冒号；补充说明→括号或逗号；轻停顿→逗号或拆成两句。
- **机器排版字符**：`…` 换成 `...` 或删；句中乱入 `→`、`•`、`·`、`▪` 改成文字或拆句；技术/英文 Markdown 里弯引号 `“”`、`‘’` 改成直引号（中文全角引号是正常排版，不要误删）。
- **复制粘贴残留**：`oaicite`、`turn0search0`、`contentReference`、`[cite: 1]`、`[cite_start]`、`[span_1]`、`grok_card`、`ppl-ai-file-upload`、无来源的 `[1][2]` 角标、`【】`/`†` 引用脚手架、结尾自动带出的 `Sources:` / “参考资料”、开头“好的，下面是……”等。全部删掉。

**反例**：删破折号不是“骗检测”；目的是让文字真的像人打的。不要因为“某个词在词表里”就无脑删，先看有没有实际信息。

### 2. 识别结构性 AI 把戏，把形式还原成观点

- **否定式排比**：`不是 A，而是 B` / `It's not X, it's Y`。一篇出现两次以上就要警惕；直接说 B，删掉前半句的铺垫。
- **强制三连**：`创新、灵感、行业洞察`、`更智能、更高效、更人性化`。两项或一项具体往往比三项更真。
- **清单化一切**：一两句话也要列点、每段挂 `##`、整句拆成 `-`、`1. 2. 3.` 框架、`- **Term:** description` 机械内联头、`TL;DR` / `核心要点` / `划重点` 标签、`---` 分割线、两三条信息也塞表格。
- **判断标准**：这个格式你会不会打给朋友/同事的微信？不会就删；结构只留给真实步骤和真需要扫读的对照表。

**例子**：`我们做了三点优化。第一，……；第二，……；第三，……` → `我们把登录从 3 秒降到 0.8 秒，并把错误提示改成可点的按钮。`

### 3. 砍掉无源权威、假深度、假范围与同义词循环

- **无源权威**：`研究表明`、`专家指出`、`业内普遍认为`、`Experts argue`——后面没有具体研究/数字/人名就删掉，或把结论用自己语气说出来；空挂一个权威比没有还虚。
- **假深度**：`highlighting/emphasizing/underscoring/reflecting …` 这类 -ing 尾巴、中文“彰显/凸显/深刻体现了……”；删掉空分析句。
- **夸大意义**：`标志着…关键节点`、`作为…的见证`、`为…奠定基础`；换成具体事件、日期、数字。
- **假范围**：`从 X 到 Y` 但 X、Y 不是真尺度；改成直接列举。
- **同义词循环**：同一个对象不停换名（模型/系统/助手/引擎）→ 选最清楚的一个重复使用；重复读起来是精确，不是词穷。

### 4. 素材不足时先补材料或标缺口，不要“补人味”

去 AI 味**不能以编造事实为代价**。只有空泛观点时，加“生动细节”就是造假：

- 作者提供了观点/经验/数字/例子 → 用这些材料改。
- 只有空稿或没来源的初稿 → 问 2–4 个关键问题，或标 `〔素材缺口〕`，交出“可保留骨架 + 待定问题”；不要用口吻、emoji、假坦白、假自嘲、鸡血把空白填满。
- 有真实样本时先读样本（句长、用词、开头习惯、标点、重复词），按样本改；没有样本不要凭空“学某个人”。

**反例**：`“这是改变世界的产品”` 不能改写成 `“我们团队凌晨三点还在打磨”`——没有依据就不写；技术文也不需要“真诚告白”来显人味。

### 5. 中文 AI 味专项：翻译腔、套话结构与伪平衡

- **互联网套话**：赋能、打通、闭环、抓手、链路、底层逻辑、颗粒度；“一、二、三”段头、`首先/其次/再次/最后`、【】段头、三短句排比、一句两个以上四字成语、强行升华/鸡汤收尾。
- **翻译腔**：`作为一个…`、被字句滥用、`不仅…而且…`、`对…进行…`、`使…得到…`、`用户们`、`…之一`、`当你…的时候，它会…`，以及用身体动作词写抽象（“接住高并发”“被流量击穿”——中文有现成说法）。
- **形容词+冒号替读者判断**：`逻辑很清晰：先建索引再查询` → 删掉定性词，让事实说话：`先建索引再查询。慢在每次全表扫。`
- **伪平衡**：`任何事都有两面性`、`既要…也要…`、`具体问题具体分析`——要写就写出“分什么情况、各自结论是什么”，否则等于没说。

**反例**：中文全角引号、必要的技术术语不删；真正的对比/转折不要一刀切。

### 6. 别从“冷冰冰”滑向“表演式热情/伪平衡”

另一种 AI 味是“假装有人味”：

- 谄媚/附和开头：`好问题！`、`你说得对`、`当然可以！`、`我很乐意帮忙`。
- 假热情：`We are excited to share`、`希望本文对你有帮助`、`让我们一起…`、`将带你…`。
- 虚假亲密度：`我向你保证`、`这是真正的领导力`、`让人遗憾是`——说具体事实，不要演情绪。
- 过度谦辞/伪平衡：`抛砖引玉`、`个人浅见`、`仅供参考`、`两方面都很重要`。

有人味来自判断、具体、承认复杂，不是套人设。技术/法律/接口文档保持中性，不等于没人味；没有真实经验就不写第一人称。

### 7. 验证升级：计数、grep、替换测试、结构对照

改写后不要只凭“感觉顺了”：

- **痕迹密度**：统计命中模式数 / 100 词；>3 算重，>6 建议重写而不是修补。
- **确定性 grep**：用精确字符串扫 `—`、`……`、`→`、`oaicite`、`turn0search0`、`[cite:`、`Sources:`、固定套话表——自检最易漏的是这些。
- **可替换性测试**：把一句话抽出来，如果它能原样出现在另一个项目的文档里，说明它没有承载本项目信息，重写。
- **结构对照**：改后逐项核对命令、URL、文件名、数字、错误码、边界条件、引用来源是否还在；尤其不能为了“更像人”把技术细节洗掉。
- **朗读测试**：改完念出来，不像你会跟朋友说的话就再改；但“念着舒服”不是唯一证据，事实完整性优先。

**反例**：检测器分数不是目标；“没被检测出”不能证明写得好，也不要为了降分制造错字/假口语。

### 8. 按场景与真实样本定语气，不用一套万能“人味”

- 技术文档/README/PR：用默认干净模式，保留术语、步骤、警告；不要加“随手打”式口语。
- 个人博客、社交媒体：才考虑带人味质感（少量倒装、语气词、残句），但**绝不碰数字、名称、链接，不做改义错字**。
- UI/界面文案：用界面里真实可见的标签，动词开头、正面表述：`点击“保存”`；`登录以继续` 优于 `您不能未登录继续`；错误信息给出具体原因和下一步：`无法保存，请检查网络` 优于 `出错了`。
- 有作者声音样本时，样本优先级高于通用风格规则；但样本不能改变事实。
