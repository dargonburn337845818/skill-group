# 开发工作流共识（完整版）

> 适用对象：编码、重构、模块/插件开发、以及任何需要“规格→执行→验证→交付”闭环的工作。
> 产出物：一份可执行、可检查的开发门禁，而不是“认真一点”的口号。
> 本文件遵守 `work-consensus` 的深模块原则与 `dsh-optimization-consensus` 的运维安全底线。

## 0. 一句话共识

```text
先冻结接口与验收，再小步实现；每个“完成”都必须有可复现证据，每个检查都必须见过变红。
```

## 1. Frame / Interview：先对齐再动手

### 1.1 北极星

- 为谁：用户/调用方/下游模块。
- 处境：什么场景下使用、当前痛点。
- 价值/可观测结果：完成时能看到什么具体变化（如命令输出、测试通过、界面元素）。
- 非目标：明确不做什么，防止范围蔓延。

### 1.2 歧义消解

- 用选择题而非开放题：给出 2–3 个选项 + 权衡，一次只问最高信息增益问题。
- 涉及关键取舍（接口形状、错误策略、配置默认值、兼容范围）必须用户确认，不擅自决定。
- 用户说“我感觉不对劲”时暂停，重新审查假设。

## 2. Plan / Spec：先画地图，再写规格

### 2.1 模块地图

先画：

```text
<模块> : <职责> : <公开接口> : <测试入口>
```

- 用 Deletion Test 判断模块是否值得存在：删掉它，复杂度是否散落到 N 个调用方？若是则保留/深化；若复杂度消失则删除。
- 接口不只签名：类型、不变量、错误模式、调用顺序、配置方式都是接口。

### 2.2 规格单

L1 组 / L2 小类必须包含：

| 字段 | 含义 |
|---|---|
| spec | 这组/这步交付什么，含负面声明 |
| accept | 可测量的验收条件（correct 模式）或可复现感受（experience 模式） |
| do | 开发执行形态：self / subagent / workflow / daemon / mixed |
| verify | 验证形态：self / subagent / redteam / dual / workflow |

- 缺任一门，不进入下一阶段。
- 不要用“我看着没问题”代替 accept；验收必须能被第三方检查。

## 3. Adversarial Spec Review / Gate：先被挑刺，再放行

### 3.1 对抗审查

- 独立视角（另一个 agent / 人 / 工具）审查规格。
- 每项记录：`BLOCKER`（阻断交付）、`GAP`（缺信息）、`NOTE`（提醒）。
- 至少跑六项检查：范围完整性、接口稳定性、错误路径、边界/反例、测试可观测、外部依赖/安全影响。
- 若没有发现，写“none found” + 已跑六项检查；不能只写“没问题”。

### 3.2 门禁

- 规格文件存在。
- 对抗审查段落存在。
- 无未决 BLOCKER。
- 若门禁被设计成“防止跳过”而非“防止故意绕过”，要诚实说明：结构门只能证明存在，不能证明质量。

## 4. Build：分层执行

### 4.1 主线程与子代理

- 主线程：规划、接口设计、集成、审查、验证。不写大块 feature 代码。
- 子代理：实现被明确切割的小块。
- 给每个实现 agent 的简报必须包含：
  - 它拥有的文件、不能碰的文件；
  - 必须保持的不变量；
  - 要运行的命令/测试；
  - 输出/验收产物。
- 重叠文件集串行，不并行。
- 子代理不碰 git 状态（不 commit、不 push、不重置）。
- 模型分层（按需要）：
  - haiku：只读机械工作（取证、扫文件、填模板）。
  - sonnet：可编辑的机械工作（改测试、小修）。
  - opus：判断/设计/复杂审查。

### 4.2 Churn-breaker

- 同一文件连续多次编辑仍不收敛（例如第 3 次），停止在主线程上继续磨，把失败输出交给一个全新子代理重新接管。
- 长循环通常不是“再试一次”能解决的，换上下文往往更有效。

### 4.3 深模块纪律

- 简单接口 + 丰富实现；不要为了“对称”创建只有一个实现的虚假接缝。
- 文件系统就是模块地图：目录/命名直接反映功能边界，新人不看文档也能导航。
- 每个模块顶部渐进披露：是什么 → 怎么用 → 类型/接口 → 实现细节。

## 5. Verify：证据化验证

### 5.1 证明分类

| 类型 | 证明 |
|---|---|
| static | 源码/commit/config 原文 |
| runtime | 测试日志 + 命令/退出码 |
| data | 可复算指标/基准 |
| rendering | 实际产物/截图 |
| tooling | 版本/依赖/API 可用性 |

### 5.2 接口是测试面

- 测试必须通过公开接口跑；测不动说明接口设计有问题。
- 先写测试锁死对外行为，实现可以交给 AI 重写。

### 5.3 Prove It Can Fail

- 对关键检查做一次“故意破坏→变红→恢复→变绿”。
- 没见它失败的检查只能标“已运行”，不能标“已验证”。

### 5.4 in-flight 阻断

- 验证/测试仍在运行时，不允许把 PASS 写进提交或发布。
- “跑完了”与“成功结束”不是一回事；等真实退出码。

## 6. Review / Ship：集成复查与终验

### 6.1 Review 范围

- 不是只看当前 staged diff，而是看“上次审查之后改过的所有内容”。
- 修复本身可能引入新 bug，所以修完必须重跑完整验证。

### 6.2 Commit gate

- 提交前做一次有界复查；CRITICAL / IMPORTANT 未决则阻断。
- 有 in-flight 验证运行时阻断提交。

### 6.3 终验清单

- [ ] 测试通过（通过公开接口）。
- [ ] 真实启动/冒烟通过（不只是类型检查）。
- [ ] 每个关键检查 `checks_observed_red` 非空。
- [ ] 规格 accept 逐条有证据。
- [ ] 无未处理 BLOCKER/GAP；redteam 项已独立裁决。
- [ ] 路径手册/README 更新；模块地图与文件系统一致。
- [ ] 运维安全：若涉及 DSH/插件热更，已按 `dsh-optimization-consensus` 隔离与回滚准备。

## 7. 简单用户话术

> 开发我会按“先定接口和验收 → 画模块地图 → 给你确认规格 → 小步实现 → 用证据证明完成”走。完成不是我说“好了”，而是测试真的从红变绿、关键检查真的见过失败、对抗审查没有未决 BLOCKER。
