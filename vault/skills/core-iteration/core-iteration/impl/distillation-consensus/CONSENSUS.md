# 蒸馏共识：把高价值内容变成 Agent 可调用的技能

> 本文档从网络公开的“内容蒸馏成 Agent Skill”实践、知识蒸馏研究与本地 `teacher-consensus-skill` 经验中，提炼出的一版可执行共识。
> 适用对象：书、长视频、播客、博客、访谈、题解、源码说明、官方文档等原始材料。
> 产出物：agent 可直接调用的启发式技能 / 共识 / 提问协议，而不是“一段读后感”。

## 0. 一句话共识

**蒸馏不是摘要压缩，而是把“不可执行的内容”改造成“可执行的结构”。**

一条真正可执行的知识，至少要同时具备五块：

```text
触发条件（什么时候用）
+ 动作（具体怎么做）
+ 反例/边界（什么时候失效）
+ 来源（这句话从哪来）
+ 简单用户话术（用一句话告诉用户方向与方式）
```

没有触发条件，它只是百科；没有反例，它只是鸡汤；没有来源，它只是模型幻觉；没有简单话术，它只是内部文档。

## 1. 三条不可妥协底线

1. **来源可追溯**：每条结论必须能指出处（URL / 题号 / 章节 / 原始 quote）。没有来源的“圈内常识”只能标 `common-lore`，并降权。
2. **人比模型有最终否决权**：蒸馏不是让模型自证正确。遇到“我感觉不对劲”、用户直觉冲突、环境异常，必须停下来重新检查，不允许硬套模板。
3. **面向用户必须简单**：最终给用户的是“方向 + 方式 + 什么时候别用”，不是原始概率、术语表、专家原话长文。

## 2. 什么算“高价值内容”，什么算“可执行技能”

### 2.1 高价值源材料

优先级从高到低：

1. 专家/作者亲手写的第一手材料：题解、访谈、post-mortem、官方文档、源码注释。
2. 多来源反复出现的同一主张：editional、社区讨论、不同作者的独立转述。
3. 带完整推理链的材料：为什么这样做、为什么失败、边界在哪。
4. 可复现的样例：小 case、代码、评分标准。

低优先级：只有结论没有推理的营销文案、纯转发无出处的内容、单一来源且无法验证的“秘笈”。

### 2.2 可执行技能的基本形态

```text
名称：一句话说清它是什么
触发：什么情况下应该调用它
动作：1-3 个可检查的具体步骤
反例：什么时候它不工作 / 容易误用
来源：至少一个可追溯引用
用户话术：用简单语言说出来的一步方向
```

如果要进入软件/矩阵，再补：

```text
feature_hint: 它对应哪个特征问题
confidence:  0~1 置信度
agreement:   多专家/多来源的一致程度
counterexample: 失效边界
question_templates: 可由程序动态生成的问题
```

## 3. 蒸馏循环（九步）

```text
1. 定目标
2. 选语料
3. 切片段
4. 提原语
5. 交叉验证
6. 编造成品
7. 校验
8. 校准/回测
9. 人类复核
```

### 3.1 定目标

先问：这次要产出什么？

- 一个可执行的工作流 Skill？
- 一套启发式判断规则？
- 一组提问协议 / 决策树？
- 一份机器可读的共识 JSON？

不先定类型，后面的“蒸馏”容易退化成“摘要”。如果目标不清，先向用户问一个问题，不要猜。

### 3.2 选语料

原则：

- 只选与目标直接相关的 5–20 个高价值片段，不要“全文进来全文出去”。
- 同一条主张找 2–3 个独立来源再升为共识。
- 冲突的主张不要急着删：保留为分支，往往比抹平更有信息量。

### 3.3 切片段（Episode）

把原始材料切成最小推理单元，而不是整段总结：

```text
问题上下文
→ 我观察到什么
→ 我暂时试了什么
→ 为什么有效 / 失效
→ 最终选了什么
→ 什么边界会推翻这个想法
```

示例：

```text
原文：
  “Since the answer is monotone, we can binary search.”

Episode：
  trigger: 求最早可行值，可行性随参数单调
  action: 先写 check(x)，把最优化变成判定
  boundary: check 不单调 / 有多个峰时不能直接二分
```

### 3.4 提原语（Primitive）

把多个片段中“同一件事的不同说法”合并成一条原语。合并规则：

- 不同说法但同一动作 → 合并。
- 一个长原语包含两个独立动作 → 拆开。
- 专家 A 主张 X、专家 B 主张 Y → 不要平均，保留两个分支。
- 每条原语必须带 `source_refs`。

### 3.5 交叉验证

- 多专家 / 多资料重复出现 → `consensus`，权重高。
- 单一专家独特风格 → `style`，低权重但保留。
- 针对常见错误的反指示 → `warning`，作为约束/排除条件。
- 无直接引用但圈内普遍认同 → `common-lore`，中等权重，必须标注。

**不要简单平均不同专家。** 分歧本身是信息，可以保留为两个分支，而不是抹成一条。

### 3.6 编造成品

成品可以是：

- `SKILL.md`：给 agent 直接加载的指令文件。
- 共识文档：`触发 / 动作 / 反例 / 来源 / 用户话术` 的集合。
- JSON：机器可读的 primitive + 概率修正 + 方向权重。
- 提示词模板：可放进系统提示的固定段落。

编造时要求：

- 不要贴整篇原文，只保留可执行骨架和必要的原始 quote。
- 不要用“必须”“永远”代替“我一般会”；区分专家口气和普适规则。
- 不要只写正向案例；每个动作都配一个反例或失效边界。
- 最终用户层一定要写“简单语言提醒”，否则 agent 能懂用户不懂。

### 3.7 校验

交付前至少检查：

- [ ] 每条有 source_refs？
- [ ] 每条有 trigger / action / boundary？
- [ ] 所有“不确定”都不能被当成“否”？
- [ ] 没有把单一风格写成普遍共识？
- [ ] 没有把推测写成专家原话？
- [ ] 用户提醒是否不用术语、只说方向和下一步？
- [ ] 用 3–5 个真实案例“干跑”一遍，确认能按步骤执行？

### 3.8 校准 / 回测（需要数值时）

如果蒸馏结果要进入概率矩阵或推荐系统，不要停在专家直觉：

1. 从目标分布中抽 20–50 个真实样本。
2. 对每条规则/特征做二值标注。
3. 统计频率，做 Beta 平滑：`P_calibrated = (count_true + prior_strength * P_expert) / (count_total + prior_strength)`。
4. 回测指标：Top-1/Top-3 命中率、平均提问数、收敛熵、用户“不对劲”率、校准误差。
5. 只保留让指标变好的原语；有争议的进入 shadow 模式不展示。

### 3.9 人类复核

- 给用户看一张“来源表”：哪条来自谁、是原话还是推断、置信度多少。
- 允许用户说“我感觉不对劲”，这不是错误，而是新信息。
- 如果用户明显看到更好的路径，机器不应以概率模型否决。

## 4. 启发式技巧库

以下是蒸馏过程中常用、且被多个实践验证过的启发式。

### 4.1 先暴力，后优化

先做“最笨但完整”的提取：把相关段落全部标出来，再压缩。不要一开始就追求漂亮模板，容易漏掉关键反例。

### 4.2 规模决定复杂度

对内容也一样：先看材料规模和目标规模。目标技能若只需要 5 条规则，就不要硬塞 50 条；如果目标是全领域矩阵，就不要只取一篇博客。

### 4.3 找一个“不会变”的东西

蒸馏里的“不变量”就是来源、ID、字段结构。无论怎么改写，`source_refs` 和 `id` 不能丢。丢了就无法审计、无法回测、无法拒绝幻觉。

### 4.4 不直接给结论，先“问”系统

当要生成对用户的提示时，不要直接说“你应该用二分”。先问：

- “答案随某个量单调吗？”
- “这个方向能一次性排除多少候选？”
- “有没有更简单的暴力基线？”

只有问题本身能区分选项时，才值得问。

### 4.5 一次只问一个高信息增益的问题

与用户交互时，不要同时抛多个提示。选择当前最能把候选空间砍半的问题。信息增益近似为：

```text
IG(q) = H(P) - E[H(P | answer(q))]
```

只有显著改变候选分布的问题才值得保留。文笔好但不区分选项的问题应删除。

### 4.6 用 MDL 选择最短仍可用的版本

最佳共识不是最长版本，而是：

```text
最短且仍能预测/引导的版本
```

如果删掉一段后行为不变，就删掉。长文不等于深刻。

### 4.7 “不确定”是弱证据，不是否定

在贝叶斯更新里，“不确定”既不是“是”也不是“否”。建议把两种后验各取一半权重：

```text
w[uncertain] = 0.5 * w[yes] + 0.5 * w[no]
```

把“不确定”当“否”会制造虚假确定性，是常见错误。

### 4.8 人类接管是元纪律

“我感觉不对劲”不是解题方法，也不是某个算法方向。它是元纪律：当用户认为模型方向不对、环境/术语异常、或需要人工介入时，允许无条件退出自动流程。不要把“人类接管”当作一个算法选项来教。

### 4.9 先判定再重构

遇到“存在性 + 构造性”混合任务，先写一个最简判定器，再用判定过程留下的信息重建答案。这比直接写复杂生成逻辑更稳。蒸馏时也一样：先判断“这条规则是否真的能区分选项”，再决定是否把它写成完整流程。

## 5. 反模式（防坑清单）

1. **把摘要当蒸馏**：只有主题概述，没有 trigger/action/boundary。删除。
2. **无来源的“专家说”**：编造 quote 或把推断写成原话。降权并标注。
3. **平均分歧**：把两个截然不同的专家观点揉成一条“50% 共识”。应保留为两个分支。
4. **只给正向例子**：没有反例/失效边界的规则会误导人。补边界。
5. **长文自嗨**：输出几千字没有可执行步骤。压缩为骨架。
6. **跳过校验/回测**：只在聊天里说“看起来不错”。用样例干跑。
7. **术语泄露给用户**：给用户看内部特征名、算法名、概率值。应转换为简单语言。
8. **让模型自己证明自己**：没有来源表、没有人工复核。加来源与人类评估。
9. **把“不确定”抹成否定**：丢失了弱证据。用弱权重保留。
10. **一次问太多问题**：用户会迷茫。一次一个最高信息增益问题。

## 6. 简单语言提醒用户（模板）

这部分是“面向用户”的出口，也是本共识与普通知识库的关键区别。

### 6.1 开始前

> 我先把材料里的高价值片段挑出来，再提炼成可执行的判断方法。不会给你一整篇复述。

### 6.2 交叉验证时

> 同一句话我会找 2–3 个独立来源才标成“共识”；只有一个来源的，我会标成“风格”并降低权重。

### 6.3 交付时

> 我给你的是三样东西：**方向**（现在该往哪边想）、**方式**（下一步具体怎么做）、**边界**（什么时候这条路不通）。

### 6.4 出现分歧时

> 如果哪条和你的直觉冲突，请直接说“我感觉不对劲”。我会停下来检查是不是我蒸馏错了，而不是硬把模板套上去。

### 6.5 用户只想要方向时

> 我先给一句话方向；你想深入时，我再展开成具体步骤和反例。

## 8. 成品发布与评测门槛

蒸馏的终点不是“一段好读的文案”，而是“能被发现、被调用、被证明有效的 Skill”。

### 8.1 元数据与可发现性

- `description` 必须第三人称，包含“做什么 + 何时触发”；这是模型发现 skill 的唯一索引。
- 名称具体、可读、尽量用动名词；避免 `helper`、`utils`、`documents` 这类通用名。
- 边界：description 写流程会让发现变差；应写“问题域与触发条件”。

### 8.2 渐进披露与瘦身

- SKILL.md 保持简短：概览、流程、边界、路由；细节放 `references/`。
- 引用一层深：SKILL.md → reference，不要让 reference 再链 reference（模型可能只读部分）。
- 重复的机械判断写成脚本/命令，不要用散文反复描述。
- 若某个 reference 不值得按需加载，它就不属于这个 skill。

### 8.3 先写评测任务（Skill TDD）

- 新增/修改 skill 前先写 1 个 prompt 场景 + 确定性 checks；复杂 skill ≥3 个。
- 至少 1 个 anti-trigger 场景：任务与 skill 无关时不应触发。
- 提示词中不要点名 skill；否则测的是提示而非发现/执行。
- 确定性 verifier 是权威；LLM judge 只做诊断，不改分数。
- 经典指标：分辨率（resolution rate）、Pass@k、Skill Lift、Skill Invocation Rate。
- 用 oracle 验证“任务可解且 verifier 没坏”；CI 设 threshold-resolution / threshold-lift，缺基线时 lift 门禁 fail-closed。

### 8.4 发布前的最终验证

- 用 `skill-verification-consensus` 输出校验报告：claims / checks_observed_red / evals / adversarial_review。
- 每个关键检查必须“见过变红”：故意破坏→变红→恢复→变绿，否则只能写“已运行”。
- 有真实使用数据时回填 `value-effect-audit`；没有则明确写“无真实 A/B”，不要用模板数据冒充。
